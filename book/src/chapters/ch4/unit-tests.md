# Unit-тестов мало

## Введение

Любой проект нужно тестировать. Лень, тяжело, больно, плохо, но это нужно делать. Для компилятора тесты
--- это показатель надежности. Добавив одну безобидную фичу в компилятор, можно что-то сломать вообще в другой
части компилятора, что критично. Тесты не дадут запушить ошибочный код. Unit-тестирование это, кончено,
хорошая практика, но когда речь идет о работе компилятора или любого другого транслятора, unit-тесты становятся
узким горлышком и ужасным методом тестирования. Допустим, нужно протестировать такой код:

```pebble
fn main(): int32 {
    return 0;
}
```

Чтобы это сделать, нужно создать файл `test.pebble` с исходным кодом теста, `test.cpp`, который будет
запускать полный цикл компиляции из драйвера в `pebble-core`. Чтобы тест можно было запустить (например,
через тот же `ctest`), нужно его скомпилировать. Тестов в компиляторе может быть сотни, а то и тысячи.
Компилировать тысячи `.cpp`-файлов, в которых 90% кода одинакова, очень долго и нерационально.

## File-based тестирование

Нужно придумать, как не компилировать `.cpp`-файлы, чтобы тестирование работало. Для этого нужно написать
**движок тестирования**, который будет читать `.pebble` файлы и тестировать их.
Но тестирование файлов может происходить по-разному. Где-то нужно проверить, что ошибок или предупреждений
**вообще нет** (позитивные тесты), а где-то наоборот --- проверяется их **наличие** (негативные тесты).
Если речь идет про негативные тесты, то было бы неплохо проверять сам текст ошибки и её позицию. Но как движку
понять как тестировать файл и что проверять для конкретного файла? Добавим так называемые **директивы** ---
команды, которые понимает только движок тестирования. Эти команды будут подсказывать движку как и что
проверять. Но как эти команды передавать? Пусть эти команды будут находиться в комментариях. Так сам
компилятор не будет обращать на них внимания.

## Директивы

Директивы будут задаваться как обычный человеко читаемый текст. Не будем писать сложных парсеров синтаксиса
директив. Парсинг будет осуществляться регулярками. Вот небольшой набор команд, который позволит покрыть
все наши текущие нужды:

1. `expect-error: <code> <text>`/`expected-error: <code> <text>`, где `<code>` --- код ошибки (из `DiagCode`),
а `<text>` --- текст ошибки. Сообщает движку, что ожидается некоторая ошибка на той же
строке, где расположена директива.
2. `expect-token: <code> <text>`/`expected-token: <code> <text>`, где `<code>` --- тип токена
(из `TokenKind`), а `<text>` --- значение токена. Сообщает движку, что ожидается некоторый токен на той же
строке, где расположена директива.
3. `mode: <mode>`, где `<mode>` либо `positive` (позитивный тест), либо `negative` (негативный тест).

Теперь можно написать, например:

```pebble
// mode: positive

fn main(): int32 {
    return 0;
}
```

или

```pebble
// mode: negative

` // expect-error: EInvalidChar "unknown character '`'"
```

Если тест позитивный, но воспроизводит ошибку ИЛИ тест негативный, но ошибки не генерирует --- тест
завершается как ошибочный. Такое поведение позволит жестко контролировать стабильность работы компилятора.
Движку останется только находить директивы через регулярки, собирать их, запускать компиляцию и сравнивать
сохраненные директивы с реальными данными (диагностика или поток токенов). Но есть у этой системы один изъян,
который помешает нормально писать тесты. Что делать, если на одной строке минимум две ошибки или два токена,
которые нужно проверить? Придется удлинять строку, из-за чего её содержимое быстро вылезет за экран и
читать файл теста станет неудобно. Чтобы исправить это можно ввести смещения строк. Это целое число строк,
на которое смещается действие директивы. Например, директива может быть написана на 2-ой строке, но её
требуется применить к коду на 5-ой строке. Или директива на 5-ой строке применяется для кода на 2-ой строке.
Пусть в нашем движке смещение указывается сразу после имени директивы (перед `:`) таким образом:
`@N`/`@+N`/`@-N`, где `N` --- смещение (неотрицательное целое число). Таким образом теперь можно записать
предыдущий тест так:

```pebble
// mode: negative

// expect-error@+1: EInvalidChar "unknown character '`'"
`
```
