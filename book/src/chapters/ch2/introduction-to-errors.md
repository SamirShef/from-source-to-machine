# Как красиво намекнуть, что человек не прав?

## Введение

Минимум в 90% случаев компилятор получает на вход невалидный или незавершённый код. Ошибки могут быть
лексическими (неизвестный символ), синтаксическими (пропущенная скобка) или семантическими
(несоответствие типов). Когда компилятор натыкается на проблему, он должен не просто «упасть», а
доходчиво ответить пользователю на три главных вопроса:

* **Где ошибка?** (`файл:строка:столбец`)
* **Что именно пошло не так?** (суть проблемы)
* **Как её можно исправить?** (подсказка)

Каждый компилятор формирует отчёты по-своему. За эталон визуализации в **Pebble** мы возьмём подход из языков
Rust и Swift — с понятными указателями, вырезкой кода из файла и цветовыми акцентами. Например, при поиске
неизвестной переменной вывод будет выглядеть так:

```rust
fn main() {
    println!("{}", x);
}
```

```text
error[E0425]: cannot find value `x` in this scope
 --> src/main.rs:2:20
  |
2 |     println!("{}", x);
  |                    ^ not found in this scope
```

## Анатомия диагностики

Система сообщений компилятора отвечает далеко не только за критические сбои. Полный спектр диагностических
сообщений обычно делится на несколько градаций:

1. **Errors (Ошибки):** Критические проблемы. Компиляция останавливается (или блокируется фаза генерации кода).
2. **Warnings (Предупреждения):** Код корректен с точки зрения синтаксиса, но содержит потенциальные баги,
антипаттерны или нарушение стандартов кода. Предупреждения не останавливают сборку.
3. **Notes (Заметки / Примечания):** Не являются самостоятельными сообщениями. Они идут «в связке» с
ошибкой или предупреждением, чтобы предоставить контекст (например, указать место, где функция была
первоначально объявлена).
4. **Help (Подсказки):** Практические советы по устранению проблемы. Компилятор предлагает конкретное
решение, если уверен в нём.

Пример предупреждения с подсказкой и заметкой из Rust:

```rust
fn main() {
    let x = 10;
}
```

```text
warning: unused variable: `x`
 --> src/main.rs:2:9
  |
2 |     let x = 10;
  |         ^ help: if this is intentional, prefix it with an underscore: `_x`
  |
  = note: `#[warn(unused_variables)]` (part of `#[warn(unused)]`) on by default
```

## Зачем нам отдельный движок диагностики?

В учебных проектах часто грешат хаотичными вызовами `std::cerr << "Error: variable not found\n";` прямо
из середины парсера или семантического анализатора. Этот подход быстро превращается в хаос:

* Текст сообщений размазан по всему исходному коду компилятора.
* Невозможно проверить вывод ошибок в автоматических юнит-тестах.
* Нельзя отсортировать ошибки по их положению в файле перед выводом.
* Сложно подавлять «лавину» вторичных ошибок, вызванных одной первой опечаткой.

Всё вместе --- ошибки, предупреждения, заметки и подсказки --- образует подсистему **диагностики**.
Заложив под неё чистую архитектуру в самом начале, мы избавим себя от боли на всех последующих
этапах разработки.
